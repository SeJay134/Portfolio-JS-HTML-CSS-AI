# Phase 3 — Blog Studio Editor architecture and delivery plan

Status: proposal for review; documentation only. Build on the reviewed Phase 2 code and PR #50 dependency fixes. No merge, paid services, hosted migration, hosted storage or production feature-flag activation is implied. Keep React/TypeScript, existing Vite multi-entry site, Supabase Auth/RLS and Vercel. Preserve current public portfolio, public Photo Compressor and AI chat.

## 1. Product experience

Private /admin/blog/ remains behind RequireBlogAdmin and a separate proposed editor enable flag (default off). Desktop workspace: searchable/filterable post list (draft/published/archived), editor canvas, inspector for title, slug, description, category/tags, byline, cover, SEO and status. Mobile: single-column list/editor/settings views, touch controls and keyboard accessibility. Reuse existing site theme, navigation and typography. English UI by default consistent with current app; multilingual content supported. No third-party AI or additional hosting in MVP.

New article starts as draft. Add/reorder/delete blocks using accessible buttons (drag optional); preview with the same renderer as the public article; save explicitly and debounced autosave after validation. Display unsaved/saving/saved/error/conflict states. Never silently discard changes; navigation warning; memory-only unsaved content initially (no persistent browser draft cache). Clear sensitive state, media URLs and queued requests on logout, account switch, admin denial or session revocation. Recheck authorization for every server operation, not only mounting the page.

## 2. Current code and compatibility

- src/components/BlogAdminPage.tsx is a gated placeholder; src/auth/RequireBlogAdmin.tsx and blogAdmin.ts are existing access gates.
- src/data/blog.ts BlogBlock supports heading, paragraph, quote, code and unordered list; content is JSON array, no arbitrary HTML. src/data/blogRemote.ts rejects unknown block types; src/components/BlogContent.tsx renders escaped React text. Do not write new block types until reader, validator and preview support them.
- public.blog_posts stores title/slug/description/category_id/author_name/content, cover fields, status, featured, reading_minutes, SEO fields, timestamps; content limit 1 MiB and current cover paths are same-origin relative. Existing category/tag/join tables and private author binding remain. Published rows are anonymous-readable only if published_at <= now. Current admin policies permit direct CRUD; must be narrowed before adding publication lifecycle.
- Existing src/lib/photoCompressor.ts exposes compressImage, targetBytes, createZip; default 300 decimal KB; JPEG, longest side capped at 2200 px, browser decode/quality search and dimension reduction. Existing standalone tool additionally checks input limits and runs moderation, supports up to 300 files. Do not fork compressor or bypass its public tool policy. See docs/PHOTO_COMPRESSOR.md.

## 3. Data design and editor contract (proposed)

Separate editable drafts from publicly visible snapshots. Keep public.blog_posts as the compatible published projection (existing static/live reader contract); use a protected editable working copy plus immutable revision snapshots in new reviewed migration. Do not autosave over an already published row. Draft tables must have RLS, no anonymous privileges, admin-only reads and validated writes. Store private author identifiers, audit events and revision history outside the public projection. Exact schema/table names subject to migration review; do not expose private/blog_internal schemas.

Proposed draft fields: post_id UUID, version bigint, content_schema_version, title, slug, description, structured blocks, taxonomy IDs, cover asset ID, public byline, SEO metadata, updated_at, author reference; revision snapshot stores validated content/taxonomy/asset references and timestamp. Derive reading time from plain text; preserve UTC timestamps; normalize and reserve unique slugs server-side. Initial published slug immutable unless explicit redirect/migration plan. Enforce limits (existing title 240, description 2000, slug 160, JSON 1 MiB; stricter editor limits may be agreed); require category, summary, valid content and alt text on publish. Drafts may be incomplete. Treat input as unknown, validate exact shape and byte counts both server and client; use plain structured JSON, no raw HTML, scripts, embeds or external arbitrary image URLs. Later rich text: allowlisted marks (bold, italic, links with http/https or approved internal relative paths), heading levels, ordered lists, image/gallery blocks with asset UUIDs; renderer must validate URLs and escape text, reject dangerous schemes, malformed nested structures and excessive sizes. Introduce versioned reader before editor emits extended schema; preserve legacy articles. Avoid an editor framework dependency until block-editor MVP proves insufficient.

Atomic operations (proposed): create draft, save draft(expected_version, idempotency key), restore revision as a new draft, publish(expected_version), archive/unpublish. Explicit server-side role/session check for every mutation; derive caller from auth.uid, not request payload; transaction locks/CAS prevent stale-tab writes; taxonomy and snapshot update together. Use restricted invoker RPC wrappers with internal helpers only when necessary, fixed empty search_path, fully qualified names, narrow EXECUTE grants and RLS. Remove direct table mutations that could bypass state/validation (including direct public projection edits by admins). Security tests for ordinary, anonymous, disabled, blocked and revoked users, and direct API bypass. Distinguish not authorized, validation error, conflict, temporary failure. No service-role key in frontend or VITE_*.

## 4. Photos and batch compression

MVP: select files from desktop/iPhone, local thumbnails, target per file (default 300 KB = 300000 bytes), progress (queued/processing/ready/failed/cancelled/uploading/saved), individual retry/remove, actual source/output size and reduction, cancel, ZIP download optional (no ZIP required for uploading to blog). Originals stay on device. Use existing compressor as shared core; extract/reuse validated batch preparation rather than weakening standalone moderation. Start with JPEG output, no SVG/HTML, HEIC only if actual browser decodes, EXIF/GPS removed by re-encoding, alpha flattened on white, animated formats not preserved. Warn for quality reduction; never upload a file exceeding chosen limit. Proposed input caps: 25 MiB/file, 40 MP, up to 300 selections (existing tool limits), sequential compression and 50–100 suggested batches on iPhone; bounded total queue bytes/preview URLs and upload concurrency (1–2). Enforce byte/dimension limits before or during decode wherever possible, release canvas/bitmap/object URLs promptly; allow cancellation and discard in-flight results. Process and release incrementally to avoid accumulating originals/ZIP memory. Test 100+ photos and corrupt/unsupported/oversized files, EXIF orientation, Safari touch and memory behavior; 300 is a maximum selection, not a device guarantee.

Media Manager: select processed photo, edit alt/caption, choose cover, insert image/gallery blocks, show dimensions and bytes; remove unused media only after references checked. Proposed data: asset UUID, immutable random object key, MIME, bytes, width/height, validation status, SHA-256 for optional scoped duplicate detection, private creator, timestamps; post/revision/asset reference relation with FK and uniqueness. Do not use user filenames as storage paths. Preserve per-use alt/caption, dimensions; use lazy loading and prevent layout shifts. Never publish original uncompressed file automatically. Optional responsive variants after MVP; no paid image transformation API required.

## 5. Storage and media security design

Use existing Supabase Storage, private bucket(s), no public bucket for draft assets. See https://supabase.com/docs/guides/storage/buckets/fundamentals and https://supabase.com/docs/guides/storage/security/access-control. Private bucket access is controlled by RLS. Validate exact Storage API behavior locally with pinned CLI/SDK and actual publishable key. Bucket MIME and byte caps alone are insufficient; client compression/moderation can be bypassed.

Design gate before implementation: isolated admin-authorized quarantine upload; bounded server-side validation of actual JPEG signature, decode/dimensions and byte length, normalization/re-encoding as needed, reject active/polyglot content; only verified assets become ready. Use existing server runtime or reviewed local adapter, no new hosting. No public upload endpoint or anonymous write. Client cannot mark assets ready or write directly to verified namespace. Any privileged server capability requires explicit live session/allowlist check, strict scope, no arbitrary key/path, no frontend secret, abuse/rate limits and independent review. Prefer scoped user-RLS operations when sufficient; if service credentials are needed for quarantine promotion, keep server-only and prove no bypass. Respect existing prohibited-content policy; automated client screening is best effort, not proof of content safety or consent. Admin-only workflow and human review; do not enable public submissions.

Public media route proposal: same-origin /blog/media/<asset UUID>.jpg, resolve via published projection/reference relation and ready verified object only, fetch private Storage object using anonymous access constrained to published references by RLS (or equally restrictive reviewed server authorization if unsupported). Never issue public long-lived signed URLs or make a whole bucket public. Direct object read/list, unverified objects, old versions, guessed paths and signed-URL issuance must be tested; no private drafts through any route. Author previews use authorized fetch to memory blob URLs, revoke when leaving. Route validates UUID/extension, fixed upstream, no redirects to arbitrary URLs/SSRF, correct image/jpeg + nosniff, no-store for MVP, bounded response. Confirm direct Storage/CDN behavior and unpublish invalidation; if direct anonymous signed URL creation or cached reads can bypass immediate revocation, use a server-only private read path with explicit publication checks instead. Never claim previously copied images can be recalled.

Publish only after every referenced asset is ready, validation and transaction succeed. Object-store/database operations not atomic: immutable objects, quarantine, idempotent retries, bounded orphan cleanup via Storage API only, never delete directly from storage.objects. No object deletion while referenced by any draft/published revision per retention policy. Archive/unpublish immediately removes public projection eligibility and media access; verify old direct URL and CDN invalidation. Retention/quota policies and backup/restore of DB plus objects required before hosted activation.

## 6. Public publication and SEO

Current dynamic Vercel slug shell is JS-dependent/noindex and HTTP 200 for missing articles; Vite dev does not reproduce Vercel rewrites (docs/BLOG_DATA_PHASE_2D.md). Keep public production flag off. Prototype publishing locally using synthetic content only. Before real publication choose request-time server render of published rows using existing Vercel deployment (preferred proposal; verify quotas/runtime) or explicit rebuild/invalidation pipeline with durable failure handling. Preserve canonical routes, HTTP 404 for missing/unpublished and 503 for upstream failure, metadata/OG/Twitter, Article JSON-LD safely escaped, sitemap and RSS from public-only rows; no draft/preview URLs in feeds/sitemap/index. Ensure actual no-JS HTML and direct refresh; no long-lived caches until invalidation proven. Keep admin/preview noindex/no-store. Scheduled publishing, version history UI, AI assistance and analytics are later additions, not launch shortcuts.

## 8. Cost and open decisions

Target zero new recurring paid services; reuse existing Vercel/Supabase plan only after checking actual quotas for DB, file storage, egress, function payload/runtime and backups. A 100-photo batch at 300 KB each is at most 30 MB of JPEG output (excluding metadata/variants); 300 is at most 90 MB. These are estimates, not an assurance of free-tier capacity. Show storage consumption, set budgets/limits, no automatic paid upgrades. No paid library, AI or image API in MVP. Review proposed limits, rich-text features, asset retention, SEO server strategy and identity-testing exception before relevant phase. No implementation or hosted changes in this PR.
