# Phase 2C — admin authorization

No production migrations, real email or role assignments. The rollout switch VITE_ENABLE_BLOG_ADMIN defaults off; existing Google sign-in and public blog stay unchanged. The admin shell is /admin/blog/ and noindex, absent from sitemap. No article editor or draft payload yet.

The signed caller must have a live auth.sessions row matching the JWT session_id and UID, a Google provider claim and OAuth AMR, a confirmed email and verified Google identity in auth.identities, active profile and enabled private allowlist. Google must remain the only permitted admin login provider; provider claim alone is not proof of which provider initiated a linked-account session if other providers are enabled. Reject accounts with any non-Google identity, third-party OAuth client claims and client-bound sessions. Do not enable other providers or identity unlinking for administrators without reviewing existing sessions. Verify actual OAuth JWT/identity behavior in staging before activation. Session lifetime settings and logout semantics also need integration validation.

The RPC public.resolve_blog_admin() is SECURITY INVOKER with no parameters. It calls one narrowly granted SECURITY DEFINER in blog_internal, a non-exposed schema with USAGE for authenticated only. private stays closed. The function locks profile and allowlist rows, binds UUID and Google subject once, then assigns role. Returning users cannot override explicit demotion, blocked status, disabled binding, or transfer an existing binding. A privileged operator may later manage allowlist only through approved protected DB operations. Never put real administrator emails in migrations or public config.

RLS is tightened to check current session on every administrative statement. Public reads remain unchanged. Revoking a session or disabling allowlist denies subsequent admin operations even with a previously valid JWT. UI checks are secondary, fail closed on backend failure, and recheck on retry/focus. Callback enrollment is best effort and gated so ordinary login does not depend on the new migration. No service-role key or new dependencies.

CI: existing 34 RLS assertions updated with synthetic session rows, additional transactional enrollment/session tests, unit gate tests and noindex/disabled smoke test. CLI is not available in authoring runtime; migration timestamp manually chosen after existing version and CI must validate it. No hosted schema changes. Before activation, review security advisors, migration history and backup, run real OAuth staging tests, approve migration deployment and only then enter owner email privately. Keep blog_internal and private out of Data API exposed schemas.
