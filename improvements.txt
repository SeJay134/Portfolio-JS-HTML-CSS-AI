LOCAL AI RUNTIME DECISION — October 7, 2026

Current hosting policy:
- The public portfolio remains a static Vercel deployment and must work without AI.
- The Flask/RAG/Ollama backend is hosted only on Sergei's own computer at this stage.
- Do not add a paid/free cloud AI server yet. Revisit hosting only after an explicit
  owner decision.
- Normal local AI startup is `python -m llm.app` on 127.0.0.1:5002.
- ngrok is not part of the normal runtime and is not required for the public site.
  It may be used only as a short-lived, explicit test tunnel.
- Never put a local API key or other secret in VITE_* variables or public browser code.

Local API security baseline:
- bind Flask to loopback only (127.0.0.1), never 0.0.0.0 by default;
- validate Host against localhost/127.0.0.1 unless a test tunnel is explicitly allowed;
- allow CORS only from configured local frontend origins; CORS is not authentication;
- keep requests stateless: no process-global chat history;
- accept only a JSON object containing a string `message`, trimmed to 1–300 chars;
- cap request bodies at 16 KiB, rate-limit requests and allow one model generation
  at a time by default;
- never log user messages or model replies; return generic errors with request IDs;
- do not serve repository/static files through Flask;
- run with debug/reloader disabled in the app.py entry point;
- if a temporary tunnel is explicitly enabled, add its host/origin to configuration
  and require an API key. That key is suitable only for private testing, never for
  embedding in the public Vercel frontend.

This decision supersedes earlier text that treated ngrok or a remote backend as
the next default deployment path. Production AI hosting is deferred.

2. FINDINGS IN THE CURRENT PROJECT

F01 [P1, UI] index.html/css/index.css: the portrait and navigation occupy a
    permanent area. On small screens, this becomes a fixed top panel with a
    height of 130/160px. There is no hamburger button or controlled drawer.
F02 [P1, UI] Styles contain repeated media-query blocks, fixed dimensions,
    min-width rules, and large offsets. Examples include margin-left:418px
    for message actions and negative footer offsets. These create risks at
    intermediate widths; confirm specific overflow cases in a browser.
F03 [P1, UI] Multiple font families, decorative shadows, and translucent headings
    weaken the hierarchy. Confirm contrast concerns with actual measurements.
F04 [P1, projects] js/index.js requests /users/sejay134/repos in the browser.
    There is no curated selection of featured work or API pagination.
    Every preview assumes main/preview.png. Missing homepage values become
    href="No website available.". Descriptions depend on hover tooltips,
    which are inconvenient on touch devices.
F05 [P0, contact] Leave a Message only creates a DOM entry and logs to console.
    It does not send or persist a message. Name/email/message values are inserted
    through innerHTML, an unsafe HTML-injection path even with local-only input.
F06 [P1, accessibility] #chat_button is a clickable div without native button
    behavior. Chat lacks a dedicated Send button and complete focus handling.
    Form inputs lack real label elements; a label attribute is not a substitute.
    Social links reuse id="link" and contain icons without accessible names.
F07 [P1, chat] fetch does not check response.ok; 400/429/500 responses can appear
    as "No response". There is no timeout, stop/retry, pending guard, or response
    ordering protection. Submission requires Enter. Error text hardcodes hours.
F08 [P0, backend] llm/app.py stores chat_history globally within the process.
    The regular chat path can use another visitor's messages. This is a verified
    storage-design issue, not evidence of a specific observed data leak.
F09 [P0, API] str(data.get(...)) runs before type validation, converting numbers
    and objects to strings. A nonempty JSON array has no .get and can cause 500.
    The 300-character limit, MAX_CONTENT_LENGTH, and rate limit already exist;
    preserve these protections.
F10 [P1, configuration] js/config.js hardcodes an ngrok URL. It recognizes
    localhost but not 127.0.0.1. Flask currently uses port 5002. Separate
    environment URLs from source code and document local/public workflows.
F11 [P1, RAG] Regular chat and run_rag use different instructions. RAG does not
    receive SYSTEM_PROMPT or history and combines instructions/context into a
    user message. Router uses English keywords and a fixed L2 threshold of 1.4.
    Retriever does not discard FAISS sentinel id=-1 when too few results exist.
F12 [P1, startup] Retriever loads its index during app.py import, requiring
    index/metadata files beforehand. README describes rag_text.txt, whereas
    indexer reads data/base/. watcher.py is entirely commented out.
    The repository has no tracked requirements/pyproject, package.json,
    automated tests, or CI configuration.
F13 [P1, behavior] js/index.js forces scrollTo(0,0) on load and focusin and changes
    zoom/overflow. This can interfere with deep links and mobile input.
F14 [P2, payload] p5.js is loaded for a 64x64 button animation. The tsParticles
    bundle is also loaded although initialization is disabled. Review and remove
    legacy chat JS/CSS variants after regression checks.
F15 [P1, SEO] Current index.html lacks a standard meta description, OG card,
    and canonical URL. A page title already exists and should be preserved.

3. LAYOUT OPTIONS AND COMPONENT PLACEMENT

Option A: recommended left drawer overlay.
  Header, 64-72px: a Menu button and name/monogram on the left; theme and Contact
  on the right. Center the main area within approximately 1120-1200px.
  Navigation starts closed on every screen and opens from the left on click.
  Benefits: more room for projects, consistent desktop/mobile behavior, and no
  text-width jump. Tradeoff: sections are hidden. Compensate with Projects and
  Contact hero actions and a visible "Menu" label next to the icon.

Option B: a 64-72px desktop rail that expands to 280-320px.
  The collapsed rail shows section icons with accessible names. The expanded
  panel overlays content. Mobile uses Option A. This creates a stronger app-like
  appearance but permanently occupies some horizontal space.

Option C: a desktop push-menu that shifts the main area.
  Use only on wide screens with a deliberately allocated grid column.
  Drawbacks: more responsive complexity, changing line lengths, possible jumps.
  Do not choose this for the first release; evaluate Option A with real visitors.

Recommended page order:
  1) Hero: name, concise specialization, 1-2 sentences about the value of the
     work, View projects and Contact actions, and Resume if a file is available.
     Desktop: roughly 60% text and 40% portrait/small scene. Mobile: text and
     actions first, followed by a compact portrait.
  2) Featured Projects: 3-4 selected case studies, followed by All projects.
  3) Skills: Web / Python & Data / AI & RAG / Tools, linked to examples.
  4) Experience: a compact timeline with 2-3 meaningful points per role.
  5) About: brief personal context and working approach.
  6) Contact: email/LinkedIn/GitHub and a working form if a backend is available.
  7) Footer: copyright, contacts, and a back-to-top action.
  Keep chat accessible at bottom-right without covering Contact or safe areas.
  Avoid a public Messages list for private inquiries.

Project card:
  16:10 preview -> title -> problem/result in 2-3 lines -> 3-5 technology tags
  -> Live demo when available + Code + Details. Details explain personal role,
  solution, limitations, and a verifiable outcome. Do not invent impact metrics.
  Desktop: 2-3 columns; tablet: 2; mobile: 1. A portfolio should curate GitHub work.
  Present the AI/RAG assistant's architecture as an engineering case study.

contract change. Do not accumulate unrelated phases in a long-lived branch.

several drafted frontend areas. Treat it as a one-time transition exception:

  4) accept Phase 5 (frontend architecture/tooling),

14. MANDATORY ENGINEERING PROCESS

This process is the default technical workflow for all future portfolio changes.

Change scope:
- One branch should normally represent one roadmap subphase, one bug fix, or one
  explicit contract change.
- Branch from the latest verified main. Keep branches short-lived.
- Do not mix opportunistic refactors, unrelated UI changes, RAG changes, and
  deployment changes in one slice.
- Every behavior change must update or add the smallest appropriate automated
  test and, when user-visible, an acceptance scenario.

Pre-merge gate:
1) Scope is complete and documented.
2) Unit tests pass.
3) Relevant integration tests pass.
4) Regression tests for touched behavior pass.
5) Smoke tests pass against the production build or preview.
6) Required E2E/browser tests pass.
7) Typecheck, lint, and production build pass.
8) Contracts in docs/CONTRACTS.md remain compatible, or the contract change is
   explicitly documented with tests.
9) ROADMAP.md and docs/VALIDATION.md record the accepted checkpoint.
10) No known P0/P1 defect is hidden by skipping or weakening a test.

Merge and release gate:
- Merge only after the pre-merge gate is green.
- Deploy the merged main branch.
- Run post-deploy smoke checks against the deployed site when automation exists.
- A person opens the deployed site in a real browser and verifies the critical
  journey affected by the change.
- Record the production verification in docs/VALIDATION.md.
- Only then is the slice closed and the next feature branch allowed to begin.
- If production verification fails, roll back or create a focused hotfix.

Commit policy:
- Prefer a small number of coherent commits inside a short-lived branch.
- Do not create a new branch for every trivial edit, but do not keep unrelated
  completed work unmerged.
- Delete merged branches unless intentionally retained as release references.

15. TEST ARCHITECTURE AND OWNERSHIP

All automated tests, fixtures, and test scenarios live under tests/. Production
source files must not contain test files. The canonical layout is:

tests/
  unit/          deterministic component/module tests
  integration/   contracts between internal modules or API layers
  e2e/           complete browser user journeys
  smoke/         minimal fast checks for build/deploy health
  regression/    tests protecting previously fixed defects/accepted behavior
  future/        scenarios for planned features; never failing CI placeholders
  fixtures/      reusable deterministic test data
  scenarios/     manual acceptance and release-gate checklists
  setup/         test-runner setup only

Rules:
- A test has one canonical home. Do not copy the same test into smoke/regression/E2E.
- Every fixed regression should add a regression test when practical.
- Smoke tests remain intentionally small and fast.
- Future tests describe expected behavior before implementation; when implemented,
  move/convert them into unit/integration/E2E/regression and remove stale plans.
- Unit and integration tests must not depend on public internet services.
- Live Ollama/RAG evaluation is a controlled acceptance activity using fixtures;
  it does not fabricate an automatic accuracy score.
- Manual browser/device scenarios belong in tests/scenarios and are evidence for
  acceptance, not substitutes for automated coverage.
- CI runs fast deterministic checks on each branch. Full browser regression runs
  on pull requests and main. Future scenarios are never executed as passing tests.

See tests/README.md for commands and suite ownership.

16. CONTRACTS BETWEEN PHASES AND PROJECT PARTS

The canonical contracts are documented in docs/CONTRACTS.md. They are release
boundaries, not informal assumptions.

Phase contract:
- A phase may consume only behavior that an earlier phase has accepted and documented.
- Changing an accepted contract requires updating its tests and running dependent
  regression suites.
- A downstream phase cannot silently redefine an upstream contract.
- Acceptance evidence belongs in docs/VALIDATION.md; roadmap state belongs in
  ROADMAP.md.

Primary runtime contracts:
- Frontend <-> Flask API: endpoint, request, status, error, source-link, timeout,
  and statelessness behavior.
- RAG content <-> index: content/knowledge.json is the versioned knowledge source;
  index publication is atomic and metadata/source IDs stay compatible.
- Navigation <-> page sections: stable IDs/anchors, focus destination, active
  section semantics, and modal ownership.
- Theme <-> persistence: system/light/dark values, first-frame behavior, storage
  fallback, and cross-tab synchronization.
- Contact <-> visitor: current release prepares a local mailto/copy draft only;
  it never claims server-side delivery.
- Project data <-> UI/RAG: public project facts stay reviewed and synchronized.
- Main <-> deployment: a merged release is incomplete until deployed smoke checks
  and a human browser verification pass.

A contract change is itself a scoped engineering change and must pass the same
merge/deploy/verification cycle.
